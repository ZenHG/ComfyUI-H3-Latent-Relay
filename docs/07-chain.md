# Chain：连跑 · 词分发 · 拼接成片

> 本文件由 README（0.6.0 梳理）拆出；0.6.7 重写（Chain 会换词、也会拼片了）。
> 📐 **槽位记号**：本文一律 `[N]` = **0 起算**（UI 上第 N 个口 = `[N-1]`）。

---

`🔗 H3 Relay · Chain` 是**纯控制节点，不参与连线**（没有输入输出口），
把 **Chain + 桥 + 落盘**（以及链上用到的「Latent Load」）拉进**同一个分组框**
（框选 → 右键 → 添加分组），按钮就长在 Chain 节点上：

| 按钮 | 干什么 |
|---|---|
| ▶ Run | 按当前段号跑一次（不满意再点一次，覆盖同段号文件） |
| ✔ Approve | 段号 +1（桥/落盘同步改），排队跑下一段 |
| ⏩ 连跑 | 按 `segments` 自动循环：跑完一段 → 段号+1 → 再跑（0 = 无限）。**运行中按钮文字会变成进度**：`⏳ 连跑中 ██████░░░░ 3/10 · 采样 5/8` |
| ⏭ 续跑 | **从上次跑到的那一段接着跑**（0.6.15）。读 `output/relay_kit/<run_id>/_progress.json` ⇒ 把段号设回去 ⇒ 开始连跑。宿主卡死 / 被看门狗杀掉之后不用从头再来。⚠ 要先把 `run_id` 填上（与桥 / 落盘一致） |
| ⏹ Stop | 当前采样跑完后停止推进 |
| 🧩 拼成一条 | 把已经跑过的 N 段拼成一条成片（0.6.7）。**拼完成片路径写进 `concat_result` 格** + 弹一次提示 |
| ↺ Reset | 段号归 0，从第 1 段重来（同时清掉本轮的段记录） |

> ⚠️ **连跑中点 `▶ Run` / `✔ Approve` 会被拦下并提示**（不会把状态机静默打回 idle）。

### 怎么一眼看出「点上了没有 / 在跑 / 停了 / 错了」

连跑是**几十秒到几分钟**的慢过程，所以状态用**三条互相独立**的通道同时表达
（任一通道被前端版本差异吃掉，另两条还在）：

| 通道 | 空闲 | 已排队 | 连跑中 | 完成 | 已停止 / 需处理 | 出错 |
|---|---|---|---|---|---|---|
| **标题栏色带 + 阶段文字** | 不画 | 🟦 蓝 · 已排队 | 🟩 绿 · 连跑中 | ✅ 青 · 完成 | 🟧 橙 | 🟥 红 |
| **`status` 格字形前缀** | ⚪ | 🟦 | 🟩 | ✅ | ⚠️ / 🟧 | 🟥 |
| **按钮文字** | 原样 | — | `⏳ 连跑中 ███░░░ 3/5 · 采样 5/8` | — | — | — |

另外两件事专治「点了没反应」的观感：

- **点击瞬间按钮文字立刻变**「⏳ … · 已点击」（700 ms 后还原；若状态机已接管文字则不抢）；
- **防抖**：同一按钮 **0.4 秒内**重复点击只认第一次（连跑一次几十秒，双击 = 白烧一轮 GPU）。
  「⏹ Stop」「↺ Reset」**不防抖** —— 那是刹车，任何时候都该立刻响应。

> 色带画在**标题栏**（canvas 绘制），不是改节点的 `color` 字段 —— `color` 会被**序列化进工作流**，
> 改它等于悄悄改用户的图。空闲时不画任何东西。

### 段记录（决定「拼成一条」拼哪几段）

每次排队成功都把 `prompt_id` 记在**段号**上（`{id, seq}`，`seq` = 属于第几轮）。三条纪律：

- **同一段重跑 ⇒ 覆盖，不算两段**（否则成片里会出现重复片段）；
- **开跑第 k 段时丢掉 `stage > k` 的旧记录** —— 续接链上重跑前段，后段必然 stale
  （内容已经不是那条链了）。丢掉的段号会写进 `status`，别让它变成"拼完才发现缺段"；
  k **之前**那几段仍然有效 ⇒ 从第 3 段起连跑不必重跑前两段；
- **空洞（首尾之间缺段）不压实**：`auto_concat` 遇到空洞**直接拒拼**并说明缺第几段
  （缺段的成片比没有成片更坏）；手动「🧩 拼成一条」允许拼，但报告里必须列出缺哪段、
  哪几段来自更早一轮。⚠ **从第 k 段续跑不算空洞**（数组开头本来就空着）。

## 参数（可选格，一律在 `status` 之后追加 / **默认 ⇒ 老图行为逐位不变**）

| 格 | 默认 | 作用 |
|---|---|---|
| `prompts` | `""` | **多段各自的词**：用**单独一行 `---`** 分块，第 k 块喂第 k 段。留空 = 不换词（老行为） |
| `prompt_target` | `""` | 词写进哪一格。留空 = 自动探测；`683` = 该节点上优先级最高的词格；`683.h3_data` = 点名到字段 |
| `auto_concat` | `false` | ⏩ 连跑结束**自动拼**成片 |
| `concat_name` | `""` | 成片文件名（不带扩展名）。留空 = 用落盘的 `run_id`；存到 ComfyUI 的 `output/` |
| `stage_index` | `0` | **现在跑第几段**（0 起算）。它决定 `prompt` 输出口给的是 `prompts` 里的**第几块**。画布上点 ▶/✔/⏩ 时**自动和桥、落盘、读上段 latent 一起改**；脚本里自己改（见 `docs/10` §7.4） |
| `run_id` | `""` | **断点续跑用**：与桥 / 落盘的 `run_id` 填一样。填了之后每跑一段把进度写进段文件同目录的 `_progress.json`；留空 = 不记进度（一个文件都不多写） |
| `concat_result` | `""` | **不用填**：拼接成功后显示成片路径（可选中复制）。⚠ 单开一格是因为写在 `status` 里会被下一条状态消息冲掉 |

### 接线：`prompt` 输出口（0.6.15 起）

```
H3RelayChain.prompt ──► 出词节点的 prompt 输入
```

🔴 **「第 k 段喂第 k 块词」是节点能力，不是前端私活。** 把上面这根线接上，
**画布手点与脚本提交图 JSON 走的是同一个节点** —— 分块算法在 `relay_core.split_prompt_blocks`
（唯一权威实现），越界（词块不够）直接报错。

- 🔴 **必须接这根线**（0.6.15 起前端那条"替你写词格"的老路**已删除**）：
  没接线时点连跑会被**当场拦下**并说明该接哪根线 —— **不会静默不换词**。
  只跑一段、不需要换词的话，把 `prompts` 留空就不会被拦。
- **接了这根线**：连线值优先于 widget 值，出词节点拿到的是 Chain 按段号取出的那一块。

## 词分发：第 k 块喂第 k 段

```
（prompts 格子里粘贴）
日式赛璐璐 2D 动画……[Shot 1] 中近景，Yuki 与 Kara 近身缠斗……
---
（第 2 段的词，开头直接接住上一段的动作与机位）
---
（第 3 段的词）
```

**词从哪来**（两条路都行）：

- **直接填在 Chain 的 `prompts` 那一格** —— 最直白，不受前端版本影响（推荐）。
- **从别的节点连线进来**（如 `easy positive`）。有连线时**以连线上的词为准** ——
  提交给宿主的就是连线值，而那一格可能还留着上一版的旧词。
  连线时 Chain 会去上游找 `positive` / `prompt` / `text` 文本格（上游只有一个文本格时也认）；
  **找不到就报错**，不会静默用回本机残留值。

⚠ 连线只认**一层**（Chain ← 上游），再往上的节点不追。

- **什么时候写**：无论手动点 ▶/✔ 还是 ⏩ 连跑，**开始第 k 段前**都会把第 k 块写进目标格。
- **块数 < 要跑的段数** ⇒ **不排队**并报错（绝不静默复用上一块 —— 那正是"以为换了词、其实没换"的坑）。
- **为什么是多行文本而不是"词目录"**：UI 用户的习惯是"在节点上改字"；让人去建
  `seg1.txt..N.txt` 是**把 API 习惯强加给 UI**。多行文本 = 一次粘贴，零文件系统操作。
- **自动探测规则**（`prompt_target` 留空时）：
  `h3_data`（第三方出词节点的 JSON 串）> 官方 `MiniMaxH3*.prompt` > 其它 `prompt`；
  **同优先级出现多个候选就报错**并列出来（让人工指定，不猜）。
- `h3_data` 是 **JSON 字符串** ⇒ 前端**解析 → 只改 `prompt` 字段 → 重序列化**，
  其余字段原样保留；解析失败或不是对象 ⇒ **拒写**并把原值留好。
- 纯函数在 `web/relay_kit_prompt.js`（**画布副本**）；**唯一权威实现在 `relay_core.split_prompt_blocks`**
  （节点与自检工具都调它，跨语言一致性由 `tests/prompt_blocks_cases.json` 两侧共读锁定），
  单测：`node tests/test_prompt_dispatch.mjs`。

## 拼接成片：包内一键，不依赖外部 ffmpeg

**段清单不猜文件名**：前端把每段 `queuePrompt` 回来的 `prompt_id` 交给后端，
后端用 ComfyUI 自己的 history 取回那一段的落盘回显 ⇒ 精确到"我刚才跑的那几段"。
没给 id 时回扫 history 找「图里带本 Chain 节点」的提交（取最近 N 次）；
再找不到就**明确报「我找了什么」**，不拼半条。

**做了什么**（口径全部沿用本仓自己的定义）：

1. **逐段体检**（拼之前就拦）：没有视频流 / 各段分辨率·fps·采样率·声道不一致 /
   **音频比视频长超过 1 帧**（= 该段音频很可能**绕过了「Trim AV」**）；
2. **画面**：流拷贝（逐包重定位时间戳，pts/dts 同加同一偏移）⇒ **零重编码、逐位无损**；
3. **音频**：整段解出 ⇒ 每段「去编码器 priming（`AUDIO_ENCODER_PRIME_MS`，同 `AudioSeam.join_prime_ms`）
   → 截到本段**有效时长**（= 帧数/fps，同 `join_audio_segments` 的 `segment_seconds`）」⇒ 重编码；
4. **四项断言**：帧数守恒 / PTS 无洞 / DTS 递增 / A·VΔ ≤ 1 帧；
5. 断言不过 ⇒ 片留着取证，报告写明**别当成品用**（不悄悄删、也不假装成功）。

**实测**（4 段 / 702 帧 / 29.25 s，672×1184）：

| 量 | 值 |
|---|---|
| 耗时 | 探测 0.12 s + 拼接 1.26 s + 断言 0.02 s ≈ **1.4 s** |
| 画面 | 成片首帧与源段**逐位相同**（对比档：全重编码 3.6 s） |
| 音频逐段落点 | **0 样本**偏差（第 1 段 1 ms）、NCC 0.999 |
| 成片 | 702/702 帧守恒、PTS 无洞、DTS 递增、A·VΔ = 0.001 s |

**退路**：默认 `video="auto"` —— 先走画面流拷贝，成片断言不过才退回**单遍重编码**重拼。

## 音轨档 / 画质档（`audio_out` · `video_crf`，2026-09-22 追加）

只影响**成片**，不影响任何段文件。画面一律**流拷贝（无损）**，所以 `video_crf` 平常根本用不到。

| `audio_out` | 成片音轨 | 实测 SNR（vs 无损源） | 什么时候用 |
|---|---|---|---|
| `aac_256k`（默认） | mp4 + AAC 256k | 40.5 ~ 50.0 dB | 默认；浏览器/剪辑通吃 |
| `aac_192k` | mp4 + AAC 192k | 38.4 ~ 44.6 dB | 想省 ~25% 体积 |
| `pcm_lossless` | mp4 + PCM f32 | **逐位一致** | 母版/归档（⚠ 浏览器预览没声音，≈4.4 MB/s） |

**音频代际 2 → 1 的机制**：段文件音轨是用户落盘编的 AAC（第 1 代）；拼接再从 mp4 解码重编 = 第 2 代。
所以「Trim AV」会顺手落一份**无损 PCM 边车**（`save_pcm`，默认开，≈2 MB/段），拼接**直读边车**：
不解 AAC、也不碰 priming ⇒ 只编一代；选 `pcm_lossless` 则**零新增代际**。

- 边车**缺失**（旧图/关了 save_pcm/该次没跑「Trim AV」）⇒ **该段**退回 mp4 解码，报告里逐段写明
  `音频源=PCM / AAC`；被静音补齐时给警告。**不 raise、不静默**。
- 边车**写失败**不影响本段渲染（日志提示 + 拼接自动退路）。
- 取回方式：节点把边车路径回显进 ui（`h3relay_pcm`）⇒ 拼接方从 history 取，**不猜文件名**。
- **段文件怎么找回来**：`pick_video_outputs` **按扩展名扫 history 的全部键**（宿主 `SaveVideo` 写
  `images`、第三方 `banzhangVideoCombine` 写 `painter_output`），条目带 `abs_path` 时优先用它
  （有些节点存到 ComfyUI output 之外）。⇒ 第三方落盘节点也能直接拼。
- **链上还有别的音频节点怎么办**（产线接线 = `裁重叠 → 音频缝 → 落盘`）：
  「Audio Seam」也落自己的边车（就是它送进落盘的那份音频）。拼接在多个候选里按
  「**与 mp4 音频长度最接近**」挑；差 > 100 ms 的**拒收**并退回解码
  （100 ms ≈ 容器 priming+尾填充的上限；J-cut 差 0.9 s ⇒ 会被干净挡下）。
  ⚠ 差得**轻微**（< 100 ms）不拒收，而是补静音 + 警告 —— 那是「边车比视频短」的正常处置。

**不开画布怎么用**：命令行 `python tools/concat_segments.py s1.mp4 s2.mp4 -o film.mp4`
（与 🧩 按钮**同一份核心代码**），或直接 `from relay_core import assemble_mp4_segments`，
或 `POST /h3relay/concat`。三者参数对应关系与脚本示例见 `docs/10` §7.4。

**宿主兼容**：`app.queuePrompt` / `api.fetchApi` 是前端内部接口，缺了就**在状态格里明说**
（不是静默失效）；`add_stream_from_template`（av>=17）缺了则**自动退回重编码**并在报告里写明原因。

`video_crf`（默认 16，0~51）只在画面**必须重编码**时生效：各段规格不一致，或流拷贝路断言不过（自动退路）。
⚠ `crf 0` 仍**不是无损**（RGB→YUV 4:2:0 色度半采样先丢）——要真无损得从**落盘节点**下手。

## 段号推进：**表驱动，五处一起动**

`stage_index` 在本包里有**五处**（`nodes.py` 里声明这个 widget 的节点 + Chain 自己）。
Chain 按一张**显式表**推进它们 —— 表就是单一真相源，漏掉哪一类会立刻在 `status` 的
「段号同步 #…」里看出来：

| 节点 | `stage_index` 语义 |
|---|---|
| 「Chain」Chain 自己 | 决定 `prompt` 输出口给的是 `prompts` 里的**第几块** |
| 「Copy Bridge」 | 本段是全片的第几段 |
| 「Latent Save」 | 同上（必须与桥一致） |
| 「Latent Load」 | **也是本段段号**（节点内部按 `stage_index - 1` 去取文件） |
| 「Audio Seam」 | **也是本段段号**（决定床文件 `audio_%05d.safetensors` 与 `joined` 拼到第几段） |

五者必须同步。历史沿革（每一次漏推都对应一次真实故障）：

- **0.6.12 前只推「桥 + 落盘」** ⇒ 「Latent Load」停在 `0`、去读 `stage -1`
  ⇒ 从第 2 段起每段都报 `stage_index=0 是第 1 段，没有上一段可续`；
- **0.6.15 补上 Chain 自己**（它决定输出第几块词）；
- **0.6.18 补上「Audio Seam」** ⇒ 在此之前它永远以「第 1 段」自居，把第 1 段的床文件
  `audio_00000.safetensors` **覆盖成第 2 段的音频** ⇒ 拼接时第 1 段拿到第 2 段的音轨
  ⇒ **成片音画错段**（画面本身是对的，只有音轨错）。
  同一次修复也救活了两个本来就坏的开关：`patch_seconds > 0` 的补丁分支
  （段号恒 0 ⇒ 永远走"第 1 段无缝可补"）与 `joined` 输出（只拼 `0..本段`）。

> 只推进**与 Chain 同一个分组框内**的那几处；某类型组内一个都没有时，**全图恰好唯一**才兜底
> （所以「Latent Save」「Audio Seam」放在分组框外也能被找到）。两套连跑组共存时兜底会退化为
> 「不动 + status 提示」—— 那时请把对应节点拉进各自的分组框。

## `run_id` 同步：**同样表驱动，六处一起动**（0.6.19）

`run_id` 是「这部片子叫什么」，决定段文件落在 `output/relay_kit/<run_id>/`。
它在**六个节点**上各存一份（`nodes.py` 里声明这个 widget 的地方）：

| 节点 | `run_id` 在这个节点上管什么 |
|---|---|
| 「Latent Save」 | 段文件写到哪个目录（`<run>/stage_NNNNN.safetensors`） |
| 「Copy Bridge」 | `ref_anchor_stage ≥ 0` 时去哪个目录读外观锚段 |
| 「Latent Load」 | 去哪个目录读上一段 |
| 「Trim AV」 | 填了才写 `<run>/appearance_log.jsonl`（E4 漂移曲线） |
| 「Audio Seam」 | 床文件 `audio_%05d.safetensors` 落在哪个目录 |
| 「Chain」 | 进度文件 `<run>/_progress.json`（「⏭ 续跑」靠它） |

**改一处 ⇒ 同组其余格自动跟随**（表在 `web/relay_kit_sync.js` 的 `RUN_ID_TYPES`）：

- 范围 = **同一个分组框**（与段号推进同一套 `nodesInSameGroup` 语义）——
  一张图里放两部片子是正常用法，跨组同步会把另一部改掉。
- 🔴 **名字冲突不猜**：同组出现两个不同的非空名 ⇒ **拦住「会提交」的按钮**并列出
  「哪个节点是哪个名字」，由你决定。段文件落进错的目录，比报错难查得多。
- **空值不扩散**：清空一格 ≠ 想把全组清空（否则误删一个字符就把整部片子的目录名清掉）。
- **兜底**：`▶ Run` / `✔ Approve` / `⏩ 连跑` / `⏭ 续跑` 四个按钮在排队前各跑一次闸，
  顺带把「唯一非空、其余空着」的格子**补齐** ⇒ 你只需要改一处。
  （有些前端版本可能吃掉 widget 回调 —— 那时由闸兜住，**不会静默失效**。）

> ⚠️ **纯前端能力**：脚本提交图 JSON 时**不生效**（脚本本来就把这一格写成同一个变量，
> 见 [`docs/10`](10-audio-seam-and-concat.md) §7.4）。
> ⚠️ **改名之后旧目录不会跟着搬**：段文件仍留在旧名字下（「目录名 = 片子名」是本包一贯语义）。

## 第 1 段：**什么都不用做**（不用手动旁路）

第 1 段没有上一段可拷，但**接线与运行都不需要额外操作**：

- 「Latent Load」在 `stage_index = 0` 时**交一个「空上下文」**（不再抛错）；
- 桥收到空上下文 ⇒ **自动直通**：latent 原样过、裁剪帧数输出 `0`；
- 段号 ≥ 1 时「Latent Load」读上一段的落盘文件 ⇒ 桥真续接。

⇒ 直接点「⏩ 连跑」就能从第 1 段一路跑下去。

**为什么不能"旁路"绕**（0.6.12 实测定案）：

- 桥的 `context_latent` 是 **required** ⇒ 不接线 ⇒ 提交校验直接报 `Required input is missing`；
- **旁路「Latent Load」同样不行** —— 宿主提交前会把 bypass 的节点"溶解"掉、把它的输入接到下游，
  而这个节点没有 LATENT 输入 ⇒ 桥的 required 输入会**从 prompt 里消失**，一样被拒。

⇒ Chain 因此**反向接管**：谁把它旁路了就自动恢复成启用，并在 `status` 里说明。

⚠ **别旁路桥**：桥没有 INT 类型的输入可透传，`trim_frames` 会变成空值。
桥被旁路时 Chain 会在 `status` 里点名提醒你按 `Ctrl+B` 恢复。

**任何按钮点了没反应** ⇒ 先看 `status` 格。0.6.12 起所有按钮回调都有兜底：
内部异常也会写成 `⚠ … 内部出错：…` 落进 `status`，不会再出现"画布上毫无反馈"。

## 状态格（点了没反应就看它）

`status` 里会写：当前段号 / 已排队 / ⚠ 分组没放对 / ⚠ 排队失败 /
第 k 段词写到了哪一格 / 块数不够 / 拼接结果与断言数字。

## 声锚（voice_anchor，0.6.19）：跨说话人续接时锁定音色

### 问题

拷贝桥把**上一段的音频尾**（约 0.9 秒）逐位拷进本段、并作为 `audio_ref` 全程钉进条件。
设计意图是"音频连续衔接"，但副作用：**上一段说话人的嗓音成了本段嗓音的生成条件**。
台词逐段换人时 ⇒ 音色交叉污染（实测：同一角色 F0 114→131 Hz、谱质心 1028→1308；
给声锚后离基准距离缩到 1/5，且生成端削顶也随之消失）。

### 实现

`H3RelayCopyBridge` 新增**可选输入 `voice_anchor`（LATENT）**：

- 接线：`LoadAudio → VAEEncodeAudio（音频 VAE）→ voice_anchor`
- 提供时：**两处同源替换** —— ① 钉住的音频前缀、② `audio_ref` 条件，都改用声锚的
  **尾窗**（窗口长度 = `context_frames` 换算的音频步数，22 帧 ⇒ 37 步 ≈ 0.925 秒）；
- 不接时：行为与旧版**逐位相同**（默认关，零迁移成本）；
- 支持三种 latent 形态：`VAEEncodeAudio` 的纯音频张量（主流）／AV 联合 latent
  （NestedTensor，取第 2 条流）／list 已拆流。

### 局限（写清楚，不藏）

| 局限 | 说明 |
|---|---|
| **锚替换整个音频尾窗** | 尾窗里的 BGM/环境垫乐也会被换掉。有垫乐的用户请把垫乐**混进声锚里**再接 |
| **情绪会被部分钉住** | 声锚的音色/语速会跟随到本段。请选与目标台词**情绪相近**的干净片段 |
| **一段多人说话只锚第一个** | `audio_ref` 只有一个窗 ⇒ 锚定的是**缝上接着说的那个声音**；同段后换的说话人靠模型自己切换 |
| **声锚时长** | 尾窗要 0.925 秒 ⇒ 声锚 ≥0.9 秒（短了按全长取用并在 report 提醒）；建议 1–4 秒 |
| **`pin_audio=false` 时被忽略** | report 会写明（降级可见，不静默） |

### 音频参考额度：本包恒占 1 个，官方那 3 个是**留给你的**（0.6.22）

| 事实 | 证据 |
|---|---|
| 官方 `ref_audios` = **Autogrow `min=0 / max=3`** | `comfy_extras/nodes_minimax_h3.py`（**UI 层**的口径） |
| **模型层没有上限** | `comfy/ldm/minimax/model.py` 是 `for blk in refs: cursor += _ref_t_span(blk)` —— 变长累加、**不截断、不校验个数** |
| 本包在 `stage_index ≥ 1` 时**恒占 1 个**音频参考 | `relay_core.apply_relay` 的 `plan.audio_ref`：接了声锚 = 声锚尾窗，没接 = **上一段音频尾**，二选一 |
| 外观锚**不占**音频额度 | `plan.anchor_ref` 是 `kind="video"` ⇒ 走图像通道 |
| 两条通道**并存，不是顶替** | 宿主先写用户那 3 个，本包再 `append=True` 追加自己的 |

🔴 **后果**：你把 3 个槽填满再接声锚 ⇒ 模型侧看到 **4 个**音频参考。
模型**照单全收**（不报错），但**超出官方口径、我们未实测** ⇒ 这是"我们让你越界了"，必须主动告知：

- **画布上**：桥节点的**标题**会直接挂一行 `⚠ 音频参考 4 个（官方上限 3）…`（不是 tooltip、不是 console
  —— 大量用户不看日志）。数字来自数你参考节点里 `ref_audios.ref_audio_N` 的**已接线**槽位。
- **report 里**：`relay_core.count_official_audio_refs` 给权威数字（脚本/API 用户看这里）。
- ⚠️ **本包这 1 个没有"完全不用"的开关**（不接声锚时用的是上一段尾窗）⇒
  要真退回官方额度，只能**自己把参考节点的 `ref_audio` 槽位减下来**。
  （本仓铁律：不做静默降级 —— 我们是**提示**，不替你丢声锚。）

### 一段内多人说话：怎么锚（0.6.21）

**先把作用域说死**：声锚回答的问题**只有一个** —— 「**缝上接着说的那个人是谁**」。
锚窗只有 ~0.9 秒（= 缝区，由 `context_frames` 换算），它替换的是**本段开头**那一段音频上下文。
⇒ **段内后续换人，锚管不到、也不该管** —— 那是 prompt 里 `<Subject N>` 的职责。

由此得到三条规则（都可由 prompt 机检，不用猜）：

| 情形 | 判定 | 该怎么做 |
|---|---|---|
| 本段首说话人 == 上一段末说话人 | **同人续接** | **不必接锚**（保留音频连续性；接同一人的锚也无害） |
| 本段首说话人 ≠ 上一段末说话人 | 🔴 **缝上换人** | **必须接锚，锚 = 本段第一个开口说话的人**（否则上一个人的音色会污染本段） |
| 本段内 ≥2 个说话人 | 锚**只覆盖缝区** | 后面换人靠 prompt 的 `<Subject N>`；**能拆段就拆段**（同段换人在音色/口型/时间轴三处都难） |

🔴 **两个最容易踩的错**：
1. **按"主角"或"这一段里戏份最多的人"选锚** ⇒ 错。要选的是**第一个开口**的那个人。
2. **指望锚把整段每个人的音色都管住** ⇒ 做不到。锚只在缝区；后面靠 prompt 声明。

**判据工具**（把上面这张表变成一条命令，不用人肉读 prompt）：

```bash
python tools/voice_bank.py advise --bank <声库目录> --prompt-file 段2.md --prev-file 段1.md
python tools/voice_bank.py advise --bank <声库目录> --speakers <角色A>,<角色B> --prev-speaker <角色A>
python tools/voice_bank.py selftest     # 说话人解析规则的自检（可证伪）
```

它按「每个 `<d>` **最近的前驱**说话人标记」算开口顺序（与 `check_h3_prompts.py` 的 L5 同源），
输出「该不该接 / 该接谁 / 本段几人」；缺锚 ⇒ 退出码 3（与 `lookup` 一致）。
⚠️ **最小格式**没有 `subject_definitions` 段（`<Subject N>` 后面跟的是动作句）⇒ 拿不到角色名，
用 `--speakers` 显式给。

### 一段内多人：两条通道怎么配合（0.6.23 调研定论）

> 2026-10-04 把宿主的参考通道**读码读到底**（不是猜），结论与上一版笔记不同，按新结论执行。

**① 参考是怎么进模型的：两条通道，同序同数**

| 通道 | 内容 | 谁生成 |
|---|---|---|
| **文本呈现** | 每个参考一个标签：`<Picture i>: ` / `<Video k>: ` / **`<Audio j>: `** | `comfy/text_encoders/minimax.py:169-191`（tokenizer） |
| **DiT 条件行** | `minimax_refs` 块列表 ⇒ 排布在目标流**之前**、**被钉住不更新**的条件行 | `comfy/ldm/minimax/model.py:396-438`（`PackedLayout`） |

🔴 **音频参考的"内容"只走 DiT；文本侧只有那个空标签**（`# audio never enters Qwen`，
`minimax.py:10`）。**标签的用途就是让 prompt 引用它** —— 官方节点自己写着
*"Use the same tags when prompting"*。两个第三方包（`minimax-h3-audio-T8`、`csglide_cast.py`）
都是同一范式：`clip.tokenize(prompt, minimax_ref_items=ref_items)` 与
`conditioning_set_values(cond, {"minimax_refs": ref_blocks})` **同序同数**，
而且**提示词不引用就不送参考**。

**② 所以本包**不做**"多塞几块"的多锚**（这是 0.6.22 之前笔记里设想的做法）

本包注入音频参考走的是 `conditioning_set_values(..., append=True)` —— **事后追加**到 DiT 侧，
而 tokenize **早就发生过了**。⇒ 追加的块：

1. **文本侧没有对应标签**（`<Audio j>` 的编号在 tokenize 那一刻就定死了）⇒ **prompt 引不到它**；
2. 让文本标签数与 DiT 参考块数**不再相等** —— 而"同序同数"正是这条通道的契约；
3. 与两个第三方实现的做法**相反**。

⚠️ 更要紧的是：**本包现有那 1 个锚的实测效果，并不能证明"无标签的块被模型采纳"** ——
声锚同时**替换了钉住的音频前缀**（`pin_audio`），两件事一起变 ⇒ 效果归因是混淆的。
⇒ 拿"1 个有效"去外推"N 个也有效"是**没有依据**的。**因此本包不实现 `voice_anchor_2/3`。**

**③ 一段里多人要各自有参考 ⇒ 走官方 `ref_audios` 槽（正路）**

```
其余人的音频 ──► TrimAudioDuration（裁到 ~0.9 s）──► MiniMaxH3ReferenceToVideo.ref_audio_N
本段第一个开口的人 ──► VAEEncodeAudio ──► Copy Bridge.voice_anchor   （本包：段级、缝区、自动裁窗）
```

- 为什么必须裁：参考行**随每一步采样**（`PackedLayout` 里 `audio_update=False` 的常驻行）
  ⇒ 参考越长越慢，而且长参考会把整段内容的音色一起带进来。
- prompt 里用 `<Audio j>` 指代（例：`<Audio 1> 是 <角色B> 的声音`），与 `<Subject N>` 配合。

**④ 🔴 `<Audio j>` 的编号**不是**槽号 —— 这是最容易踩、且**完全不报错**的一脚**

宿主 `comfy_api/latest/_io.py:1198-1211` 按 `ref_audio_0..max` **索引升序**枚举，
但 `if expected_id in live_inputs` **只把已接线的槽放进 dict**；官方节点再用
`for audio in (ref_audios or {}).values()` 交给 tokenizer，tokenizer 按**枚举顺序**发 `<Audio 1..N>`。

⇒ **`<Audio j>` 的 j = 第 j 个「已接线」的槽（按槽号升序）**：

| 你接的槽 | prompt 里该写 | 写错的后果 |
|---|---|---|
| `ref_audio_0` / `ref_audio_1` / `ref_audio_2`（连续接满） | `<Audio 1>` / `<Audio 2>` / `<Audio 3>` | 编号与槽号一致，没问题 |
| **只接** `ref_audio_2` | **`<Audio 1>`** | 写 `<Audio 3>` ⇒ **指空，且任何一层都不报错** |
| 接 `ref_audio_0` + `ref_audio_2` | `<Audio 1>` / `<Audio 2>` | 写 `<Audio 3>` ⇒ 同上 |

🔵 **本包的兜底**：槽位**跳号**时（编号会骗人），桥节点标题上会直接写出实际编号
（`web/relay_kit_refs.js::ordinalHint`，只在会骗人时开口，连续接满时不制造噪声）；
report 里也给权威口径。

**⑤ 本包注入的那 1 个怎么陈述才对**（已写进 report，别在别处说反）

它是 **DiT 侧第 `官方数+1` 个**音频参考，**没有文本标签、prompt 引不到它**，
只作为条件行被模型看到。要"可被 prompt 引用"的参考 ⇒ 见 ③。

**⑥ 🆕 第三条通道：一个槽里装多人音色（0.6.25）**

② 说的"不做 `voice_anchor_2/3`"仍然成立（那是**多块**，标签对不上）。
但 GG 想要的**多锚**其实是另一个意思：**只占一个音频参考槽，却让段 2 复刻出段 1 里所有人的音色**。
这两件事可以同时成立 —— **关键不在"几个块"，而在"那个唯一的块里装了多长的音频"**：

| | 旧口径 | 0.6.25 起 |
|---|---|---|
| 窗长由谁定 | **视频钉住窗**（22 帧 ⇒ **0.925 s**） | `audio_ref_seconds`，`0` = **自动**（实测 2~6 s） |
| 那个块里装什么 | 上一段**最后一句** | 上一段**尾部若干秒**（可含多人） |
| 额度占用 | 1 个 | **仍是 1 个** |

为什么能拉长（两条零 GPU 复现的实测）：

1. `plan_relay(audio_frames=…)` 的窗长**本来就独立于视频钉住窗**（旧代码里节点恒传 `None`
   ⇒ 白白浪费了这个参数）；实测 `a_frames` 39 → 1.625 s、96 → 4.0 s、240 → 6.575 s（取到顶）；
2. 窗的**原料就是上一段整段音频** —— `KEY_EXPORT_TAIL_AUDIO` 在宿主里**并不存在**
   ⇒ `audio_tail_from_latent` 走 `audio_from_latent` 分支，能取到**整段**。

自动定长的判据（`relay_core.auto_audio_ref_seconds`）：

- **有声** = 每格 RMS 的一阶差分 > `P99 × 0.20`（**必须用差分**：真实路径拿到的是
  **VAE 音频 latent**，已归一化，静音段 RMS 与语音段同量级 ⇒ 用 RMS 判恒得"有声格 = 0"）；
- 从尾部往前**累计够 2 秒有声**就停，**上限 6 秒**；
- 阈值取 **P99 而非 P50 / max**（四组判据横评实测，理由见 `AUDIO_REF_VOICE_REL` 的注释）。

⚠️ **代价（未实测确认，不要当已验证）**：窗里的音频**就是上一段的台词** ⇒
模型**可能复述** —— 这是理论上唯一的风险。

**已实测（2026-10-04，2 臂 243 帧）**：窗 **38 步 → 168 步**（0.93 → 4.18 秒，4.4×；
覆盖上一段的说话片段 **4 → 17 个**）⇒ 两臂都**准确说出 seg2 的三句台词、零 seg1 专有词** ⇒
**未观察到复述**。判据可靠性由**对照实验**保证：同一套 ASR 判据对 seg1 的样本 **3/3 命中
全部 5 个专有词**。⚠️ 只覆盖**一段素材、一次生成**（宿主 `er_sde` 非确定性 ⇒ 不是可复现 A/B）
⇒ 台词密集的素材仍建议自己听一遍。

⇒ **两条通道的分工**（③ 与 ⑥ 互补，不冲突）：

| 想要 | 用什么 | 占几个槽 |
|---|---|---|
| 段 2 复刻段 1 **所有人**的音色（不指定谁是谁） | ⑥ `audio_ref_seconds`（**不接声锚**） | 1 |
| 段 2 复刻**某个指定的人**（缝上换人） | ③ 官方 `ref_audios` 槽 + prompt `<Audio j>` | 官方槽位 |
| 段 2 的音色**钉死**为某个人、且管住缝区 | 声锚 `voice_anchor`（会**接管**窗长，`audio_ref_seconds` 失效并在 report 点名） | 1 |


### 兜底措施

| 兜底 | 行为 |
|---|---|
| 不接 / 锚缺失 | 完全回退旧路径（逐位不变） |
| 锚短于窗口 | 取锚全长 + `report` 提醒"建议 ≥0.9 秒" |
| 🔴 **锚没有内容**（全零 / 常量 / 静音）· 形态非法 · 含 NaN | **直接 raise**（报错可读，绝不静默装作有锚）。判据 = 尾窗的**时域标准差** < `1e-2`：`MiniMaxH3AudioVAE.encode` 返回的是**归一化** latent（`(z−mean)/std`）⇒ "有没有内容"看**方差**、不看幅值。⚠️ **零 ≠ 静音** —— 归一化空间的原点是 VAE 的**均值点**（"平均音色"）。**想关声锚请拔线，不要接空 latent** |
| 拼片侧削顶 | 组装工具 `--peak-cap 0.90`（纯线性增益，建议值；帽 0.95 会被组装 AAC 重编码过冲回 1.0） |
| 响度漂移根治 | 用**响度归一过的声锚**（峰值 0.9）—— 实测模型会跟随锚的响度 |

> ⚠️ **最容易踩的一脚**：把**出词节点的 `LATENT` 输出**接到 `voice_anchor`。
> 那是 `_empty_av_latent()` 出来的**空 AV latent**（全零），不含任何语音 —— 它**形态合法**（[B,32,2,T]），
> 所以 0.6.19 之前会**静默生效**（report 里还写"声锚生效"）。0.6.20 起**当场 raise** 并指路。
